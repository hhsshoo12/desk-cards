.dard 카드 패키지 설계

Desk Cards를 폴더 카드 앱에서 카드 플랫폼으로 넓히기 위한 카드 형식과 권한 모델입니다.

개요

Desk Cards의 중심은 폴더 카드입니다. 폴더 카드는 앱에 내장된 기본 카드이고, .dard로 옮기지 않습니다. .dard는 그 옆에 다른 종류의 카드(시계, 날씨, 시스템 상태 등)를 얹을 수 있게 하는 확장입니다. 레인미터나 Windows 7 가젯과 같은 계열입니다.

새 카드는 .dard 파일 하나로 배포합니다. 안에는 HTML 한 장과 매니페스트만 있고, 카드가 네이티브 기능을 쓰려면 Desk Cards가 WebView에 넣어 주는 desk 라이브러리를 부릅니다.

목표

  • AI가 만들기 쉬울 것: HTML/JS 한 장이면 카드가 됨
  • 설치할 때 무엇을 하는 카드인지 한눈에 보일 것
  • 설치 크기 256MB 이하 (WebView2는 이미 Windows에 있음)

1차에서 하지 않는 것

  • 완벽한 보안 (가능한 권한을 크게 줄여서 해결)
  • 프로그램 실행, 파일 쓰기, 클립보드 읽기
  • 파이썬·Lua 같은 백엔드 언어

패키지 구조

.dard는 확장자만 바꾼 zip입니다. 파일은 딱 두 개입니다.

날씨.dard  (zip)
├─ manifest.json   카드 정보와 권한
└─ card.html       카드 전체 (CSS·JS·이미지 모두 인라인)

React로 빌드하든 인라인 합성기를 쓰든, 결과물은 HTML 한 장이어야 합니다. 외부 파일·CDN은 불러올 수 없습니다.

카드 파일 위치와 불러오기

%USERPROFILE%\DeskCards\
├─ 게임\            폴더 = 폴더 카드 (지금과 같음)
├─ 작업\
├─ 날씨.dard        .dard 파일 = 카드
└─ 시계.dard
  • 한 루트에 다 둠: 폴더 카드가 쓰는 그 루트에 .dard 파일을 그냥 넣으면 카드가 됩니다. 폴더는 폴더 카드, .dard 파일은 카드입니다. 지우면 카드도 사라집니다.
  • 매번 풀어서 열기: 설치 단계가 따로 없습니다. 켤 때마다 zip을 메모리에서 열고, card.html은 WebResourceRequested로 메모리에서 바로 넘겨 줍니다. 디스크에 풀린 파일이 없어서 관리할 것도, 몰래 고칠 것도 없습니다.
  • 승인 기록은 바깥에: 사용자가 승인한 권한과 .dard 해시는 %APPDATA%\DeskCards\config.json에 저장합니다. 카드 파일이 자기 승인을 스스로 적어 넣을 수 없습니다.
  • 처음 보는 .dard나 해시가 바뀐 .dard가 루트에 생기면 설치 창을 띄웁니다. [취소]하면 그 해시는 다시 묻지 않고 꺼 둡니다.
  • 크기 제한: 풀었을 때 기준 최대 32MB. zip 헤더에 적힌 크기는 거짓일 수 있으므로(zip 폭탄), 헤더를 먼저 보고 거르되 실제로 압축을 풀면서 읽은 바이트도 세다가 32MB를 넘는 순간 멈추고 거부합니다. 파일은 manifest.json과 card.html 두 개만 허용하고, 그 밖의 항목이나 폴더 경로가 있으면 거부합니다.
  • 하위 호환 없음: 사용자가 아직 한 명뿐이라 예전 구조를 옮기는 코드는 만들지 않습니다.

manifest.json 예시

{
  "dard": 1,                        // desk API 버전 (권한이 돌려주는 필드가 이 버전에 고정됨)
  "id": "com.example.weather",
  "name": "날씨",
  "version": "1.0.0",
  "cards": [                        // 띄울 카드 목록
    { "id": "now",  "name": "지금 날씨", "ratio": [1, 1] },  // 가로:세로 비율만. 크기는 앱이 정함
    { "id": "week", "name": "주간 예보", "ratio": [2, 1] }
  ],
  "permissions": {
    "system": ["cpu", "memory", "battery", "network"],
    "notify": true,
    "system.control": ["volume"],
    "internet": ["api.openweathermap.org"]
  }
}
  • 와일드카드 금지: internet에는 도메인을 정확히 적습니다. *.example.com은 거부합니다.
  • 적은 항목만 쓸 수 있음: system에 cpu만 적었으면 메모리는 읽을 수 없습니다. 설치 창 풍선에도 적은 항목만 나옵니다.

동작 구조

card.htmlWebView2 안에서 실행. 카드마다 origin이 따로 있음
→
desk 라이브러리호스트가 페이지에 주입. desk.system.get() 같은 함수 제공
→
postMessage (JSON)카드와 호스트 사이의 유일한 통로
→
호스트 (C#)권한과 횟수 제한을 검사한 뒤 실제 작업 수행
  • AddHostObjectToScript는 쓰지 않습니다. C# 객체를 JS에 직접 노출하면 검사하지 않은 메서드가 새기 쉽습니다. 모든 요청은 JSON 메시지 한 가지 모양으로만 받습니다.
  • 권한 검사는 호스트에서만 합니다. desk 라이브러리 안의 검사는 편의용일 뿐 믿지 않습니다.
  • .dard별 origin: https://<매니페스트 id>.card.desk/처럼 가상 호스트를 .dard마다 따로 매핑합니다. 그래서 localStorage·IndexedDB가 다른 .dard와 섞이지 않습니다. 한 .dard가 띄운 카드들은 같은 origin이라 저장소를 같이 씁니다.

카드 크기와 개수

카드 UI는 card.html을 그대로 띄웁니다.

카드 틀

  • 1차는 폴더 카드와 같은 틀에 넣습니다. 테두리·아크릴 배경·모서리·선택 표시는 호스트가 그리고, 그 안을 card.html이 채웁니다. WebView 배경은 투명이라 HTML이 배경을 칠하지 않으면 아크릴이 비쳐 보입니다.
  • 옮기기·스마트 가이드·편집 모드·카드 바 넣기는 폴더 카드와 똑같이 틀 기준으로 동작합니다.
  • 틀 없이 HTML 모양 그대로 띄우는 "frame": "none"은 나중에 합니다 (투명 부분 클릭 통과, 컴포지션 WebView, 편집용 틀이 필요).

비율과 크기

  • 카드는 가로:세로 비율만 정합니다 ("ratio": [2, 1]). 픽셀·칸 크기는 매니페스트에 적지 않습니다.
  • 실제 크기는 앱(런타임)이 관리합니다. 처음에는 폴더 카드와 어울리는 크기로 놓고, 사용자가 모서리를 끌면 비율을 지킨 채 커지고 작아집니다. 카드 바에서는 바 두께에 맞춰 줄입니다. 작업 표시줄은 가리지 않습니다.
  • 카드는 받은 크기에 맞춰 그리기만 합니다. desk.card.size()/on("resize")로 픽셀 크기를 받고, CSS는 %·vw·vh·container 단위로 짜는 걸 권장합니다.

개수

1차에는 크기·개수 한도와 그 권한을 두지 않습니다. 정해 둔 한도안(면적 15%·4장, 넘으면 card.large·card.many)은 나중에 할 것에 있습니다.

  • 개수는 매니페스트에 미리 적습니다. cards 배열의 길이가 곧 카드 수이고, 실행 중에 카드를 새로 만들 수는 없습니다.
  • 파일은 여전히 card.html 한 장입니다. 카드마다 같은 card.html을 열고, desk.card.id()로 자기가 어떤 카드인지 알아서 그립니다.

카드가 있는 곳

  • 카드는 언제나 바탕화면 층 또는 카드 바에만 있습니다. 다른 앱 창 위로 올라올 수 없습니다. 그래서 큰 카드도 앱을 가리거나 다른 창을 흉내 낼 수 없습니다.
  • 나중에 "항상 위"를 넣더라도 카드끼리 겹칠 때의 순서만 뜻합니다. 바탕화면 층을 벗어나는 권한은 만들지 않습니다.

desk API 초안

  
모든 함수는 Promise를 돌려줍니다. 권한이 없으면 PermissionError, 횟수 제한에 걸리면 RateLimitError로 거부됩니다.

  

    
함수권한설명

    
desk.card.id()⚪이 카드가 cards의 어느 카드인지 (id)

    
desk.card.size() / on("resize")⚪앱이 정한 카드 크기(픽셀·배율)와 변경 알림

    
desk.cards.post(id, msg) / on("message")⚪같은 .dard의 다른 카드와 메시지 주고받기 (JSON)

    
desk.card.settings.get/set()⚪카드별 설정 (호스트 설정 창의 카드 상세에도 표시 가능)

    
desk.theme() / on("theme")⚪다크/라이트, 강조색, 배율

    
desk.openUrl(url)⚪기본 브라우저로 열기. 사용자가 누른 직후에만, http(s)만

    
desk.system.get(fields?)system현재 값 한 번 읽기

    
desk.system.watch(fields, ms, cb)system주기적으로 받기 (최소 1000ms). 호스트가 한 번 읽어서 여러 카드에 나눠 줌

    
desk.notify({title, body})notifyWindows 알림. 알림 이름은 카드 이름으로 고정

    
desk.volume.get/set(n), mute(bool)system.control시스템 볼륨 0~100

    
desk.brightness.get/set(n)system.control화면 밝기 0~100 (지원하는 모니터만)

    
desk.fetch(url, init)internet호스트가 대신 요청. 적힌 도메인·https만. 쿠키 없음

  

  

    왜 그냥 fetch가 아니라 desk.fetch인가요?

    카드 origin이 https://…card.desk라서 대부분의 외부 API가 CORS로 막힙니다. 호스트가 대신 요청하면 CORS 문제가 없고, 도메인 검사와 횟수 제한도 한곳에서 할 수 있습니다. 브라우저 기본 fetch는 CSP connect-src로 같은 도메인만 허용해 두고, 되면 써도 됩니다.

    네트워크 옆길 주의

    WebRTC는 요청 가로채기와 CSP를 둘 다 거치지 않고, 로컬 IP까지 알려 줍니다. internet 권한이 없는 카드도 밖과 통신할 수 있게 되므로 반드시 끕니다 (실행 인자 + 주입 스크립트로 RTCPeerConnection 제거). WebSocket과 DNS 미리 가져오기도 CSP·설정으로 막습니다. 구현 후 실제로 새지 않는지 테스트 카드로 확인해야 합니다.
  

  
그 밖에 카드는 배경 타이머 절전을 끕니다. 바탕화면 카드는 늘 "보이지 않는 창" 취급을 받아서, 끄지 않으면 시계가 멈춥니다.






  
스스로 업데이트 방지

  
카드가 인터넷에서 코드를 받아 실행하면 설치 때 본 카드와 다른 카드가 됩니다. 다음 네 가지로 막습니다.

  
    
    
  1. CSP: eval, new Function, 문자열 타이머, 외부 스크립트, javascript: URL, WebAssembly 금지
    2. 
    
  2. 스크립트 해시: 설치할 때 card.html 안의 모든 <script> 해시를 계산해서 script-src 'sha256-…'로 고정
    3. 
    
  3. 풀어 두지 않음: .dard를 디스크에 풀지 않고 매번 메모리에서 열기 때문에, 몰래 고칠 풀린 파일이 없음
    4. 
    
  4. 불러올 때 해시 확인: 승인할 때의 .dard 해시와 다르면 켜지 않고 설치 창을 다시 띄움
    5. 
  


default-src 'none';
script-src 'sha256-…' 'sha256-…';
style-src 'unsafe-inline';
img-src data: blob:;
media-src data: blob:;
font-src data:;
connect-src <internet에 적힌 도메인>;
worker-src blob:;
base-uri 'none'; form-action 'none'; frame-src 'none'; object-src 'none';

  

    남는 한계: 받아 온 데이터에 따라 동작이 바뀌는 건 막을 수 없습니다. 하지만 그 동작도 승인된 권한 안에서만 일어납니다. 그래서 권한을 좁게 두는 게 핵심입니다.
  

  
업데이트로 권한이 늘면 다시 설치 창을 띄웁니다. 권한이 같거나 줄면 그대로 업데이트합니다.






  
출처 확인과 서명

  
카드에 암호 서명은 넣지 않습니다. 대신 배지 두 가지를 둡니다. 둘 다 표시만 하고, 권한 확인은 모든 카드가 똑같이 거칩니다.

  

    
배지조건누가 받을 수 있나

    
출처 확인됨 · GitHub.dard 해시가 매니페스트에 적힌 GitHub 저장소의 릴리스 파일 해시와 같음저장소 릴리스에 .dard를 올린 누구나

    
서명됨출처 확인됨 + 그 저장소가 서버의 서명 목록에 있음직접 목록에 올린 저장소만

  


  
매니페스트


{
  "name": "날씨",
  "repo": "someone/weather-card",
  …
}


  
출처 확인됨 · GitHub

  
    
    
  1. 카드를 만든 사람은 그 저장소의 GitHub 릴리스에 .dard를 올립니다. 해시 파일은 따로 올리지 않습니다(GitHub가 릴리스 파일마다 SHA-256 digest를 API로 알려 줍니다).
    2. 
    
  2. 설치할 때 앱이 그 저장소의 모든 릴리스를 받아, 파일의 SHA-256과 같은 digest가 있는지 봅니다(사용자가 한 버전 전 파일을 받았을 수 있어서 최신만 보지 않습니다).
    3. 
    
  3. 같으면 "출처 확인됨 · GitHub"와 저장소 링크를 보여 줍니다.
    4. 
  

  
남의 카드를 고치고 repo를 그대로 두면 해시가 달라 확인에 실패합니다. repo를 자기 저장소로 바꾸면 확인은 되지만 자기 저장소가 표시되니 정직합니다.


  
서명됨


https://file.hhsshoo.com/desk-cards/signed.json

{
  "repos": [
    { "id": 912345678, "name": "someone/weather-card" },
    { "id": 923456789, "name": "other/clock-card",
      "releases": [ { "tag": "v1.2.0", "sha256": "3f1c…e9" } ] }
  ]
}

  

    
등록 방식서명됨이 뜨는 파일같은 저장소의 나머지

    
releases 없음 (저장소 전체)그 저장소 릴리스의 모든 파일—

    
releases 있음 (특정 버전)적힌 sha256과 같은 파일만출처 확인됨까지만

  

  
    
    
  • 특정 버전은 태그가 아니라 파일 해시로 고정합니다. GitHub는 릴리스 파일을 지우고 같은 이름으로 다른 내용을 다시 올릴 수 있어서, 태그로 고정하면 내용이 바뀌어도 서명됨이 유지됩니다. tag는 알아보기 위한 메모입니다.
    • 
    
  • 목록에는 저장소 숫자 ID로 비교합니다. 이름은 계정 삭제 뒤 다른 사람이 같은 이름으로 다시 만들 수 있지만, ID는 다시 쓰이지 않습니다. name은 사람이 알아보기 위한 메모입니다.
    • 
    
  • 목록에 저장소를 올리면 그 저장소의 이후 릴리스도 모두 서명됨이 됩니다(카드를 업데이트할 때 목록을 고칠 필요 없음). 빼면 다음 확인 때 배지가 사라집니다.
    • 
  


  
해시와 다시 확인

  
    
    
  • 파일 해시는 켤 때마다 그 자리에서 계산합니다(승인 때의 해시와 비교하는 그 값).
    • 
    
  • GitHub·서명 목록 확인 결과는 파일 해시에 묶어 저장하고 하루 한 번 다시 확인합니다. 작가가 릴리스를 지웠거나 목록에서 빠진 것을 반영하기 위해서입니다.
    • 
    
  • 오프라인이거나 GitHub 요청 한도에 걸리면 실패가 아니라 "확인 못 함"입니다. 설치는 막지 않고 배지만 보이지 않습니다.
    • 
  


  
믿는 근거

  
    
    
  • 출처 확인됨: 카드 작가의 GitHub 계정. 계정이 털리면 악성 릴리스도 출처 확인됨·서명됨이 될 수 있으므로, 배지는 표시만 하고 권한 확인을 따로 받습니다.
    • 
    
  • 서명됨: 위 + 서명 목록. 목록은 HTTPS(Cloudflare)로 받고, 고칠 수 있는 곳은 캡차 + 등록된 이메일로만 오는 매직 링크로 들어가는 파일 관리 페이지뿐입니다. 즉 그 이메일 계정도 도장입니다(2단계 인증 필수).
    •

결정 기록

  
왜 이렇게 정했는지 남겨 둡니다.

  
백엔드 언어(파이썬·Lua·Deno)를 버리고 WebView에 라이브러리를 주입한 이유
    
    
      
  • 파이썬 import 허용 목록: random._os나 ().__class__.__base__.__subclasses__() 같은 방법으로 우회됩니다. PEP 578 감사 훅도 단독으로는 샌드박스가 아닙니다.
    • 
      
  • Node: 권한 모델이 "안전벨트"일 뿐, 악성 코드 방어용이 아니라고 공식 문서에 적혀 있습니다.
    • 
      
  • Deno: 권한 모델은 매니페스트와 잘 맞지만 97MB라서 256MB 목표에 부담입니다.
    • 
      
  • Lua 5.1: 가볍지만 API를 전부 직접 만들어야 하고, AI가 카드를 만들기 어렵습니다. LuaJIT는 x64에서 메모리 제한을 걸 수 없고 ffi·바이트코드가 구멍입니다.
    • 
      
  • WebView 주입: 샌드박스(Chromium)는 이미 있고, 크기는 0MB이며, 네이티브 기능은 호스트가 JSON 요청을 검사해서 해 주면 됩니다.
    • 
    

  

  
shell을 영구히 없앤 이유
    
PowerShell 한 줄이면 파일·인터넷·사용 기록 등 다른 모든 권한을 할 수 있습니다. 막을 방법을 고민하는 것보다 API가 없는 게 가장 안전합니다. 같은 이유로 launch에서도 셸·스크립트 실행기 exe를 거부합니다.

  

  
open을 금지 목록이 아니라 허용 목록으로 한 이유
    
금지 목록은 빠지는 게 반드시 생깁니다 (.docm, .xlsm, .chm 등). 안전하다고 확인한 문서·미디어 형식만 열어 줍니다.

  

  
launch 인자를 매니페스트에 고정한 이유
    
실행 중에 인자를 자유롭게 넣을 수 있으면, 명령 실행 기능이 있는 수많은 exe를 통해 사실상 셸이 됩니다. 금지 목록으로는 다 막을 수 없습니다. 인자를 고정하면 설치 창에서 본 것과 실제 실행되는 것이 같아집니다.

  

  
파일 권한을 "선택 창 = 승인"으로 한 이유
    
매니페스트에 경로를 적게 하면 시작프로그램 폴더처럼 위험한 곳을 지정하는 문제가 생깁니다. 사용자가 Windows 창에서 직접 고르게 하면 카드는 경로를 정할 수 없고, 따로 "허용할까요?" 창도 필요 없습니다. 메모 카드처럼 자주 저장하는 카드는 카드 전용 저장소(localStorage·IndexedDB)를 쓰면 됩니다.

  

  
권한을 뭉뚱그려 보여 주는 이유
    
목록이 길고 자세하면 사용자가 읽지 않고 "예"만 누르게 됩니다. 화면에는 짧은 이름과 색만, 자세한 건 풍선에 둡니다. 실제 검사는 매니페스트의 정확한 범위로 합니다.

  

  
카드 서명·검증을 하지 않는 이유
    
서명은 누군가 카드를 검사하고 보증해 줄 때 의미가 있습니다. 우리는 대기업도 스토어도 아니라서 카드를 하나하나 검증할 수 없습니다. 그래서 "누가 만들었나"를 믿는 대신 "무엇을 할 수 있나"를 권한으로 좁게 막습니다. 설치 창에 만든 사람도 표시하지 않습니다 (확인할 수 없는 정보라서).

  

  
암호 서명 대신 GitHub 출처 확인 + 서명 목록으로 한 이유
    
암호 서명은 개인 키를 지켜야 하고, 한 번 서명하면 취소하려고 결국 서버 목록이 또 필요합니다. GitHub 릴리스 해시로 "누가 배포한 파일인지"를 확인하고, 서명 목록에는 저장소만 올리면 작가는 릴리스만 하면 되고 우리는 목록에서 한 줄로 추가·취소합니다. 일반 카드의 설치 창에는 확인할 수 없는 만든 사람 정보를 쓰지 않고, 출처가 확인된 경우에만 저장소를 보여 줍니다.

  

  
.dard를 풀어 두지 않고 매번 여는 이유
    
풀어 두면 풀린 폴더를 따로 관리하고, 고쳐지지 않았는지 지켜야 합니다. 매번 zip을 메모리에서 열면 .dard 파일 하나만 관리하면 되고, 해시도 파일 하나로 확인합니다. 카드는 작아서 여는 비용도 거의 없습니다.

  

  
WebAssembly를 막은 이유
    
wasm을 허용하면 인터넷에서 받은 바이너리를 실행할 수 있어서 스스로 업데이트 방지가 무너집니다. 게임(Canvas·WebGL)이나 이미지 처리(Canvas·WebGL·순수 JS 라이브러리)는 wasm 없이 충분합니다.

  

  
카드 수를 실행 중 요청이 아니라 매니페스트에 미리 적게 한 이유
    
설치 창에서 본 개수와 실제로 뜨는 개수가 같아야 합니다. 실행 중에 카드를 만들 수 있으면 바탕화면을 카드로 덮을 수 있고, 개수 제한을 따로 감시해야 합니다. 미리 적게 하면 확인할 것이 숫자 하나뿐입니다.

  

  
카드를 바탕화면 층·카드 바에만 두는 이유
    
카드는 HTML이라 무엇이든 그릴 수 있습니다. 다른 앱 위로 올라올 수 있으면 로그인 창이나 Windows 대화 상자를 흉내 낼 수 있습니다. 바탕화면 층에만 있으면 큰 카드라도 사용자가 쓰는 앱을 가릴 수 없어서, 나중에 만들 크기 권한도 노랑(민폐)으로 둘 수 있습니다.

  

  
1차에 카드 틀에 맞추고 프레임리스를 미룬 이유
    
폴더 카드가 앱의 중심이라 새 카드도 같은 틀에 있어야 한 앱으로 보입니다. 틀이 같으면 옮기기·가이드·편집 모드·카드 바를 그대로 씁니다. 프레임리스는 투명한 곳의 클릭 통과, 투명 창에서 보이는 컴포지션 WebView, 편집할 때 덧씌울 틀이 따로 필요해서 1차 목표와 상관없는 일이 많습니다.

  

  
크기 대신 비율만 적게 한 이유
    
화면 크기·배율·카드 바 두께가 제각각이라 카드가 픽셀 크기를 정하면 어딘가에서 어긋납니다. 비율만 받으면 앱이 상황에 맞게 크기를 정하고, 카드는 받은 크기에 맞춰 그리기만 하면 됩니다. 한도 검사도 앱 한곳에서 합니다.

  

  
1차 범위를 크게 줄인 이유
    
처음부터 완벽한 보안을 목표로 하면 끝이 나지 않습니다. 위험한 권한을 아예 빼고 시작하면, 남은 권한은 막을 구멍이 적습니다. 나머지는 실제 카드를 만들어 보면서 필요한 것부터 추가합니다.
